How tars keeps the durable store, and how it opens a SQLite file: the `DurableStore` (the task queue and every task's trajectory, in SQLite or in memory, with its schema and migrations), the port the durable store seals its journals through, and the `Db` handle every store is built from. The runtime drives tasks over the durable store; the durable store keeps what they did and decides only whether a write is admitted.

- Role (hex): adapter(SQLite) mechanism; the durable store's two backends (`SqliteDurableStore`, `MemDurableStore`) behind its ports (`durable::{DurableStoreRead, FiberStore, DurableStore}`); port (`durable::journal::TrajectoryLog`, the durable store's sealed-journal store)
- Effect budget: db (sqlx with the SQLite driver; opening a file, running the durable store's migrations and its reads and writes); the sealed-journal store it is handed (no file format of its own)
- Deps: may depend on [tars-types (tasks, statuses, events, leases, tenants), sqlx, thiserror, async-trait, tokio (sync, for `MemDurableStore`'s lock), serde_json (opaque goal, result and payload JSON) and uuid (lease tokens, durable store ids, journal file names)]; MUST NOT import [tars-melt, or any crate above the store layer → they depend on this crate, never the reverse; dev-dependencies included]
- Owns concepts: [durable::{DurableStoreRead, FiberStore, DurableStore, DurableStoreError, Writer, Holding, Cancelled, UnparkedStatus} — the durable store's interface (`FiberStore`, the reads and writes a running step makes; `DurableStore`, the runner's on top), each write landing whole, whether a write is admitted (which writer holds a task's lease), what a wake, a park and a reply do in each status, and that an ending wakes the task's continuation; durable::{SqliteDurableStore, DurableStoreInitError, ExistingDurableStore, ReadOnlyDurableStore, Unclaimed} — a durable store in a SQLite file (`migrations/durable/`), opened for a tenant or, for a tool with none, as a runner left it; durable::MemDurableStore — the in-memory backend; durable::{SealedJournal, Unsealable} — when a finished task's journal may be sealed into a file and what the seal did; durable::UntoldFailure and `DurableStoreRead::{failure, failure_reason}` — a failed task's reason, read from its last `Failed` event; durable::{recorded_tenant, retenant} — the tenant and durable store id a durable store records; durable::{journal_task_ids, read_journal_raw} — a durable store file's journals, sealed or not, read on a connection of the caller's; durable::journal::{TrajectoryLog, JournalRow, JournalFileName, BadJournalFileName, StagedFile, TaskGroup, JournalError, FindJournalError, MemTrajectoryLog, task_groups, staged} — the port a durable store stages a batch of finished journals through (one row group per task, invisible until the durable store registers the file), the in-memory store, and the layout every store writes; Db, Access, Location, DbError — the one way a file is opened (`Db::open(path, Access)`: create, existing, or read-only) and the settings each access gets (WAL, `synchronous = NORMAL`, a 5s busy timeout; an in-memory database pinned to one connection that is never recycled), and running a store's embedded migrations; is_lock_contention — which SQLite results mean another connection held the database, so another try can pass]
- Reason to change (the ONE): what the durable store records about a task and which writes it admits, or how tars opens and reads a SQLite file, changes
- Belongs here: a new durable store write or read and the event it leaves; a column or table of the durable store (a new migration under `migrations/durable/`); a rule a write is admitted or refused by; what the durable store asks of a sealed-journal store; a new way to open a file; a pragma every store needs; a new class of lock contention
- Does NOT belong: what runs next, when to sweep, seal or renew a lease, how many retries a task gets and whether an error is worth retrying → the runner that drives the store, which calls the durable store with the facts and the `now` it decided on; the clock → the caller, which passes every time in; the shape of a task's goal, result or `Delta` payload → the step or fiber that wrote it (opaque JSON here); a sealed journal file's format and where it lives → the store that implements `TrajectoryLog` (Parquet: `tars_melt::event::log::ParquetTrajectoryLog`) and the code that picks it (`tars_melt::durable_file`); the event logs' tables → tars-melt; retrying on contention → the caller; reading a SQLite file tars does not own → MCP or the sandbox, not tars

Boundary note: every caller that opens a SQLite file goes through `Db::open` or the same settings, so the open settings live in one place; a store writes its own SQL on `Db::pool()` in SQLite dialect, with no query abstraction between. sqlx is a dependency of this crate only.
