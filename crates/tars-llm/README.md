The LlmProvider trait with every concrete backend (HTTP APIs, CLI subprocesses), and the middleware chain an LlmService runs a call through — LlmService = one provider + one model + an ordered handler chain of Middleware; the one public service concept and no service trait; the provider and the middleware are held as `dyn` trait objects. Per docs/architecture/01-llm-provider.md, `stream` is the basic provider operation and `complete` aggregates it; the chain is docs/architecture/02-middleware-pipeline.md.

- Role (hex): port + adapter for the providers (HTTP: anthropic/openai/gemini/vllm; CLI subprocess: claude_cli/codex_cli and the cli dialects (claude, codex, opencode, antigravity); SDK daemon: claude_sdk; OpenAI-compatible local: llamacpp/mlx; cassette replay; mock) — trait and impls co-located by design; core for the chain framework and its middleware policies — but see friction: it composes over concrete sibling crates, not pure ports
- Effect budget: network (reqwest + SSE — this crate OWNS raw LLM HTTP for the workspace) | process (spawns CLI delegates; child_reaper SIGKILLs process groups on host signal) | fs (cassette record/replay, auth/key file reads) | clock (retry backoff, circuit-breaker timing, httpdate); the middleware reaches event storage only through an injected dependency (tars-melt's LogSink)
- Deps: may depend on [tars-types, tars-sandbox (SandboxPolicy for CLI delegates), tars-config (schema→instance in registry), tars-melt (the `llm_wire` table a transport writes its raw bytes into; the LogSink EventEmitterMiddleware writes the call log through), reqwest, eventsource-stream, tokio, sha2, nix(unix)]; MUST NOT import [a database driver (sqlx, rusqlite) → tars-melt owns storage; tars-tools → upper layers call this crate, never the reverse]
- Owns concepts: [LlmProvider, LlmEventStream, ProviderError, LlmError, BatchStatus, BatchResultItem, UnparsedToolCall, ProviderRegistry, Auth/AuthResolver, HttpClient/HttpAdapter, StreamDecodeState, WireRecorder, SchemaDialect/adapt_schema, BatchSubmitter, child_reaper, subprocess_diagnostics, every concrete *Provider + *Builder; LlmService, LlmServiceBuilder, Middleware, Next, ChainOptions, RetryMiddleware, PerCallBudgetMiddleware, TenantBudget*, CircuitBreaker, TelemetryMiddleware, EventEmitterMiddleware, validation middleware]
- Reasons to change: a backend's wire/subprocess contract changes, or a new backend is added behind the same trait; the chain contract or a cross-cutting request policy changes (order law, a new middleware)
- Belongs here: a new HTTP backend adapter; an SSE quirk fix; CLI-delegate spawn/reap logic; a new Middleware impl; a chain-order rule; Caller-attribute plumbing for a policy
- Does NOT belong: sandbox profile construction → tars-sandbox (this crate only THREADS a SandboxPolicy through); model/routing declarations → tars-config; the agent loop (call→tools→re-call) → the caller; event store schemas → tars-melt

The crate has two modules. `provider` (`src/provider/`) is the trait, the registry and the backends; it knows nothing of the chain: a backend does not retry, meter or budget, and no file under `src/provider/` names `crate::pipeline`. `pipeline` (`src/pipeline/`) is the service and its middleware; it reaches a backend only through `LlmProvider`. The crate root re-exports what callers use from both. The design is docs/design/tars-llm.md.

Note: port + many adapters in one crate is this crate's stated design (docs/architecture/01-llm-provider.md), not drift — the boundary to police is inward (the backends know no chain).

Friction (flagged): hex-purity would have the chain framework depend on ports only; in reality the crate imports the concrete tars-melt crate (which co-locates port + adapter). Accepted as workspace convention; tars-melt's storage backends sit behind its own features, so depending on it does not by itself pull in a database driver.
